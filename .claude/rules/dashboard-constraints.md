# Dashboard Design Constraints

`docs/DESIGN.md` is the visual contract (color tokens, typography roles, components) and `docs/PRODUCT.md` the product one; both are tracked, while the tooling that generated them is gitignored. These constraints in `ProxyDashboardHtml.kt`, `PathTableHtml.kt` (the Paths view's table), `ActivityHtml.kt` (the Activity view's table), `ScrapeNow.kt`, `ProxyDashboardCss.kt`, `ProxyDashboardService.kt` (the proxy's site), `ScreensHtml.kt`, `ScreensCss.kt`, and `ScreensScript.kt` (the proxy's screens page), and in `common/dashboard/` what every dashboard shares, `DashboardServer.kt` (the server, login, guards, assets, sessions, and push loop), `DashboardPage.kt` (the ids the script reads, the head, tabs, live region, status pill, history strip, and scrape-now button and result panel), `DashboardScript.kt` (the page's script), `ThemeScript.kt` (the theme button's script, which the screens page shares), `ScrapeNowHtml.kt` (what the result panel shows), `ScrapeNowLimits.kt` (the scrape-now limits both dashboards share), and `DashboardCss.kt`, are load-bearing and easy to undo by accident. The agent's dashboard (`agent/dashboard/`) is built from the same parts and keeps the same rules:

- **Every dark rule goes through `DashboardCss.darkRule`.** It writes the rule twice, under `prefers-color-scheme: dark` unless the page is set to light, and for a page set to dark (`data-theme`, from the bar's theme button), so a dark colour written as a bare `@media (prefers-color-scheme: dark)` block would ignore the button. The button stays outside the pushed status, as Log out does, and `DashboardPage.THEME_SCRIPT` stays in the head of every page, the login page's included, so a stored theme applies before the page draws. `DashboardThemeTest` pins the rule's two selectors.
- **The bar's status and every button after it stay in its tail.** `DashboardPage.barTail` holds the status, the proxy's Screens link, and the bar's end in one box, which `DashboardCss` keeps beside the tabs while it fits and otherwise moves, whole, to a row above them (`.bar:has(> .bar-tail)`'s `wrap-reverse`, so the tabs keep the bar's rule). A bar item added after the tabs but outside the tail wraps on its own, item by item: that left the theme button alone on a row, or, with the status's old `min-width:0`, drew its last stat over the tabs at about 760 to 900px. `ProxyDashboardHtmlTest`, `AgentDashboardHtmlTest`, and `DashboardThemeTest` pin it.
- **The live region must stay outside every `hx-swap-oob` region.** A region the push loop rewrites re-announces itself on every frame. `ProxyDashboardHtmlTest` and `AgentDashboardHtmlTest` pin this, each for every view's page and push.
- **The column guide stays outside every `hx-swap-oob` region, and its rows come from the header's own columns.** `DashboardPage.renderFilters` renders it under the search, where no push reaches it, so it stays open as `#path-table` or `#activity` (header and all) is replaced; inside a pushed region it would close on the next frame. Each view builds one `TableColumn` list (`PathTableHtml.columns`, `ActivityHtml.columns`, `AgentActivityHtml.COLUMNS`), and both the header row (`columnHeaders`) and the guide iterate it, so a column can't reach the header without an explanation; add a column to that list, not to the header row alone. `PathTableHtmlTest`, `ActivityHtmlTest`, and `AgentDashboardHtmlTest` pin both.
- **Check a color against `--surface-2`, not `--surface`.** Every token also lands on the tighter ground under tables and section headers, which is where all 29 of the contrast failures fixed in 4.0.1 lived. The measured AA floor is 4.59:1 — `docs/DESIGN.md` records the per-token values. `DashboardThemeTest` requires 4.5:1 there of `--ink`, `--ink-2`, `--ink-3`, `--ok`, `--warn`, and `--crit`, in all three token blocks (light, dark, and set to dark); give a new text token the same check.
- **Every layout must render agent identity through `agentLabel()`.** The agent, path, and activity views are read against each other, so a divergent label (or a raw `agentId`) defeats the correlation they exist for. That includes the detail pane of an agent that has gone, which takes its name from the snapshot (`ProxySnapshot.goneAgentName`), and says "The selected agent" when it holds none. `ProxyDashboardHtmlTest`, `PathColumnsHtmlTest`, and `ActivityHtmlTest` pin it.
- **The search matches a row as the row shows it.** `RowFilter` matches a path with its slash (`RowFilter.pathAsShown`, which the Paths and Activity rows render it with too) and, on the proxy's dashboard, an agent by its `agentLabel()`, so a search for what the table, the copied proxy URL, or Prometheus shows finds it. Match a new field as its cell renders it. `RowFilterTest`, `ActivityHtmlTest`, and `AgentDashboardHtmlTest` pin it.
- **The route base arrives already normalized; do not normalize it again per use site.** `DashboardServer` derives `routeBase` once (trailing slash stripped, so it is empty at a root mount) and hands the same value to its own `routing { }` block and to the site's `pages` and `frame`, which pass it to `renderPage`/`pushFragment`. Sub-routes are then plain interpolation. Re-adding a per-site join helper splits the rule across two layers, which is how the router and the links came to disagree before: the links were fixed while the routes still built `//paths`, and only Ktor discarding empty segments hid it. The nav's own link is the base itself, so it must render as `/` rather than collapse to an empty `href`. `ProxyDashboardHtmlTest` pins both.
- **A scrape-now stays out of what the proxy reports, and every action stays behind `pageGuard`.** `ScrapeNow` submits through `ScrapeDispatch.submitScrapeRequests`, which records nothing; the scrape route (`ProxyHttpRoutes`) records Prometheus's scrapes (`recordScrapeOutcome`, the latency and size metrics, the request counter). Don't record a scrape-now there, or it skews the rates Prometheus alerts on and fills the path's History with scrapes Prometheus never made. Its `ScrapeSpec` (`ScrapeNow.scrapeOf`) carries `ScrapeOrigin.DASHBOARD`, which sets the scrape request's `dashboard_scrape` so the agent counts it in `agent_dashboard_scrapes_total` rather than its `agent_scrape_*` metrics; keep it, or the agent's rates skew the same way; it keeps the scrape out of the filter's counts and `agent_filter_*` too (`AgentHttpService.filtered`). The agent's Scrape now (`AgentScrapeNow`) keeps the same rule from its side: it fetches through `AgentHttpService.fetchForDashboard`, which marks its request `dashboard_scrape` and counts nothing (no `agent_scrape_*`, no `agent_dashboard_scrapes_total`, no filter counts) and isn't recorded in `AgentScrapeHistory`, which `fetchScrapeUrl` fills with the proxy's scrapes alone; and it scrapes only a URL the agent already has for a path, never one a browser sends. `AgentWebDashboardTest` and `AgentHttpServiceDashboardTest` pin it. Install `DashboardServer.pageGuard` on every route the page's script calls: it checks the Origin and, for anything but a GET, requires the `HX-Request` header, which no other site's page can send without a CORS preflight the dashboard never answers; without it, a link elsewhere could make the proxy act. `ProxyWebDashboardTest` pins both.
- **A dashboard refuses framing only while its `framingEnabled` is false.** `<role>.dashboard.framingEnabled` is `true` by default, the user's choice, so a page can embed the dashboards. While it's false, `DashboardServer` installs its `DashboardNoFraming` plugin, which adds `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY` to every response (on a proxy whose `proxy.dashboard.screens` lists any, `frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN`, `Framing.SAME_ORIGIN`, refused, but for the proxy's own `/screens`; `Framing.of` decides, and the agent's dashboard, which has no screens page, never sends `'self'`), refusals, redirects, error pages, assets, and the WebSocket handshake included, so another site can't show a page under content of its own and steer a click onto Scrape now or Log out. Either way, with a login set, `CachingHeaders` gives every response but the versioned assets `Cache-Control: no-store`. Don't set either header in a route instead, or add another way to change it (a list of origins was considered and dropped for the boolean): a narrow-width check of a page uses a narrow window or device emulation, not an iframe. `DashboardResponsesTest` pins every kind of response, with a login and without, with framing enabled, and framed by its own origin only; `ProxyWebDashboardTest`, `ProxyWebDashboardLoginTest`, and `AgentWebDashboardTest` pin the setting's wiring both ways, and `ProxyScreensTest` its `'self'` with screens listed.
- **The screens page never moves a frame.** `/screens` (`ScreensHtml`, `ScreensScript`) holds a frame per screen, and a browser reloads an iframe that moves in the page, which would lose the agent or path the reader selected in it. Its layouts show, hide, and size panes (classes, `grid-column`, and the All grid's scale), never reorder or reparent them, and every frame's `src` is set in one place, `setSrc`, by the load rule: a frame loads its start the first time its pane shows, a link with a path reloads it, and a bare id never does. A link's path loses its leading slashes and backslashes before it's joined to a screen's url, so at a root mount `#proxy//host` can't load another site in the proxy's frame. The tab's state classes are `up` and `down`, so the pane's notice is styled only as `.view .down`. In All, a frame loads when its tile nears the grid's view (an `IntersectionObserver` calling `show`), never every frame at once, and never unloads; All's rows are `grid-auto-rows:max-content`, since a pane's `overflow:hidden` gives auto rows no minimum and they shrank to a tile's bar. The tabs fit one row by hiding those that don't fit (`fitTabs`, the `out` class), never by reordering them, keeping the selected screen's tab and Split's right one; each tab is measured once, in bold, and the More button at its widest label, so `mark` and `updateMore` never refit and a dot changing never moves a tab. The More menu (`ScreensHtml.MENU_ID`), a popover that lists every screen, sits outside the `<nav>`, whose `.nav a` rules would style its entries as tabs; it's placed and cleared in `beforetoggle`, before it shows, inside the window on both sides (`placeMenu`, since at a phone's width More sits nearer the left edge than the menu is wide), its search has `autofocus`, Enter in the search prevents its default, whose keypress would reach the More button and reopen the menu, and the window's `blur` closes it, since a click into a screen goes to its frame, which light dismiss never sees. Where the kept tabs and More are wider than the row, the row is `tight` and its tabs shrink, their names cut, rather than spill over the layout buttons; and a browser without popovers gets the wrapping row, every tab shown and no More (`@supports not selector(:popover-open)`). `ScreensScriptTest` and `ScreensHtmlTest` pin these.
- **Served asset URLs carry the WebJar version.** The scripts are cached for a year (`Cache-Control: public, max-age=31536000`), and a reload doesn't revalidate them, so a fixed URL would leave a browser running its cached htmx against the next version's markup. The route and the page's `<script>` tags both build the URL from `DashboardServer.ASSET_DIR` (`assets/<htmx version>`); don't serve an asset outside it. The Links column's brand icons (`LinkIcon`) follow the same rule under `DashboardServer.ICON_DIR` (`assets/icons/<simple-icons version>`), which the route and the page's icon stylesheet (`ProxyDashboardCss.linkIconCss`, in the head, so no push carries a URL) both build from. `ProxyWebDashboardTest` pins that each unversioned path 404s.
